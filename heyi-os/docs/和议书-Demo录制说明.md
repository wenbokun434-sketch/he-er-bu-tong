# 和议书｜从分歧到共同规则：Demo 录制说明

编写日期：2026-10-11。按当前项目的页面、表单和状态规则编写。

本机演示：[打开和议书](http://127.0.0.1:5173/)。先按项目 README 完成安装与启动；本副本不连接原作者的线上数据库。

## 先说明：录制操作会保存数据

首次安装不包含作者的聊天、方案或任务；程序只提供初始教学设定。脚本本身不会修改数据，实际录制时的保存与提交会写入你自己的本地数据库。不要在别人的实际协作数据上直接进行彩排。

下面的提交操作，是你准备好录制后再执行的操作。执行后会真实保存到该案例，不是临时预览。修改共享画像会使既有确认需要复核；修改方案会产生新版本；新成稿也可能取代旧成稿成为执行依据。历史会保留，但“保留历史”不等于“当前状态完全不变”。

本脚本依据当前实现核对操作路径，未在这次工作中向线上网站写入数据重演。既有版本号、消息和状态以录制当天页面为准。

## 1. 这支 Demo 要讲什么

一句话：三方不必变得观点一致，但必须把共同认可的行动、限制与复审办法写清楚。

故事采用网站已有的 **OpenAir Watch／跨国预警合作**。研究团队要速度，医院与社区要决定权，数据合规方要可追责。第一份方案虽然五项齐全，仍遭到反对；三方通过讨论，把反对意见转化为规则，再制作并分别确认完整和议书。

本次只演示虚构教学项目，所有测试数据均为合成数据。不接入真实医院、不上传患者信息、不提供医疗或法律结论。文中的“阈值”“审批”“暂停”是参与方约定的模拟规则，网站不会自动监测数据、执行审批或停止外部系统。

建议成片 15–18 分钟；首次实际操作预留 35–50 分钟。粘贴输入、等待 AI 和重复确认可加速，关键状态变化用正常速度展示。不要把剪辑后的时长描述成系统实际响应速度。

## 2. 开录前准备：不依赖清空历史

### 2.1 窗口与素材

1. 在已能访问网站的浏览器中打开网站，使用 100% 缩放，推荐 1920×1080。
2. 把本说明放在另一窗口或另一显示器，用于复制文字；关闭通知和无关标签页。
3. 不展示密钥文件、API 控制台、个人账户资料。屏幕共享时只录网站窗口。
4. 默认一人切换四个演示角色。开场明确它是“演示角色”，不能称为四个独立认证账户。
5. 可额外打开同一案例的第二窗口，保持会议室页面，展示消息同步。当前访问范围不因这次录制改变；不要假定其他同学已经有访问权限。
6. 正式录制前只查看页面、准备剪贴文本。不要先把本轮所有确认做完，再假装现场从零生成。

### 2.2 既有数据怎么处理

- 不把页面拍成“空白新项目”。开场说明：“保留历史，本轮展示一次新的教学协商。”
- 本轮统一标记为 `DEMO-01`，写进开场消息、提案说明和文书标题。它只是文字标记，不是系统提供的独立房间或数据隔离功能。
- 会议室滚到最新消息附近后开始。旧消息依然存在，AI 也可能收到最近的旧消息／分析摘要；脚本里的提问会提醒 AI 区分本轮与历史，但不能保证旧内容完全不进入上下文。
- 仍使用已有三个议题：“预警速度”“数据主权”“紧急状态定义”，无需重复新增同名议题。
- 若已有方案，按钮是“修订方案 / 发起复审”；若没有，则是“起草首个方案”。
- 不固定要求页面显示 v1/v2。下文“第一稿 A”和“修订稿 B”是剧情称呼，实际可能是 v4/v5。
- 和议书版本号独立计数。下文用 `W` 表示本次保存的实际文书版本，不要把它与方案版本混淆。
- 若另有自定义议题，本次不要删除。制作文书时只勾选本轮三个方案，其他内容不自动纳入本次试点约定。
- 三方画像要在方案确认前填妥。确认方案后，主线不再修改画像，否则会触发复核。

> 和议书不是让不同的人得到同一个答案，而是帮助他们在保留差异的情况下，形成愿意共同遵守的规则。它可以用于科研合作、校园活动或社区协商。今天我们用一个虚构的跨国预警合作项目，演示从分歧到文书，再到承诺执行的完整过程。此前的记录会保留，本轮是一场新的教学演示。

## 4. 镜头二：让每一方先说清楚自己

### 通用操作

进入“协作画像”→切换到相应参与方→“编辑我的立场”→逐项粘贴→勾选“我确认这四项内容可对项目成员公开，并进入变更记录。”→“确认共享并更新地图”。每一方保存成功后再切换。

录制可完整展示医院方填写，研究方与合规方输入加速，但要保留三方分别提交的画面。协调员不能代填。

### 4.1 研究团队：Dr. Chen

希望达成：

```text
DEMO-01：在四周合成数据试点中，保留跨地区比较和早期信号分析能力。我方希望尽量缩短更新间隔，并向合作医院回馈每周可理解的结果摘要。
```

最担心的事：

```text
如果只能每天收到一次更新，可能无法及时比较模拟信号；如果审批条件不明确，也无法稳定安排研究工作。
```

不可接受的底线：

```text
不能把合作变成完全没有跨地区比较的单点展示；不能把本次合成数据试点的结果宣传为真实临床预警能力。
```

可协商的条件：

```text
不要求原始患者数据出境。可以接受正常情况下每六小时更新，异常时另行申请限时提频；愿意公开指标用途、交付摘要并参加共同复审。
```

### 4.2 医院与社区：Grace N.

希望达成：

```text
DEMO-01：在不使用真实患者数据的教学试点中，验证医院与社区能否保留对共享范围、用途和继续参与的决定权，并获得每周可理解的结果说明。
```

最担心的事：

```text
每小时整理和审批会增加本地负担；一次同意可能被理解为长期授权；研究方临时提频后，社区没有暂停或追问用途的机会。
```

不可接受的底线：

```text
本轮不得上传真实患者或个人信息。共享范围和用途不能单方面扩大；医院与社区必须能够提出暂停，不得把未回复当作同意。
```

可协商的条件：

```text
可以授权固定范围的合成汇总信息，每六小时更新；在医院与数据合规分别明确同意后，可短期提频，但须限时、留痕并安排社区参与复审。
```

### 4.3 数据合规：Matteo R.

希望达成：

```text
DEMO-01：把每次共享和紧急提频的用途、责任人、审批、访问期限及复审结果记录清楚，让参与方能够追溯谁在什么条件下做了决定。
```

最担心的事：

```text
“紧急”成为跳过确认的理由；授权到期后仍继续使用；共享范围或方案发生变化，却沿用原来的接受记录。
```

不可接受的底线：

```text
不能绕过明确授权、用途限制与操作留痕。不能把 AI 的建议当成合规批准，也不能由同一角色报告完成并自行验收。
```

可协商的条件：

```text
可以采用预先约定的简化申请表和快速共同审核。紧急权限最长二十四小时，到期失效；续期、扩大范围或修改共同规则都需要重新确认。
```

### 旁白

> 四个栏位分别记录希望得到什么、担心失去什么、不能突破什么，以及哪里可以协商。共享的是成员主动确认的摘要，不是系统偷偷推断的私人立场。研究方并不必须拿到原始数据，医院方也不是拒绝合作，这让我们看到了可协商的空间。

验收画面：三方出现本轮内容；新提交显示“成员已提交”。如果此前已保存过完全相同内容，原样保存可能不增加记录，这是正确行为，不必为录制随意改字。

## 5. 镜头三：在会议室把真正的分歧说出来

### 操作

进入“协作会议室”。按顺序切换角色，将以下每段分别粘贴到“共享讨论内容”，点击“发送”。每段都是一条独立消息，不把角色名一起粘贴；页面会自动显示发送角色。

### M01｜协调员：本轮开始

```text
【DEMO-01 开始｜虚构教学演示】今天只讨论 2026-11-01 至 11-28 的合成数据试点，不使用真实患者信息。请区分目标、底线和可协商条件。历史记录保留，但本轮方案以接下来提交的当前版本为准。我们先解决更新频率，再明确数据控制和紧急提频规则。
```

### M02｜研究团队：时效要求

```text
我最初希望每小时更新一次合成汇总指标，这样容易观察跨地区模拟信号。但我真正不能失去的是跨地区比较能力，不是必须拿到原始数据。我也愿意把每周结果用医院和社区看得懂的方式反馈。
```

### M03｜医院与社区：不同意默认高频

```text
我不同意默认每小时更新。本地整理和核对有成本，我们也不能因为参加试点就失去决定用途和暂停的权利。正常情况下每六小时可以讨论，但临时提频必须先得到我们明确同意，不能由研究方单方面决定。
```

### M04｜数据合规：提出可追溯要求

```text
我不反对提频，但必须写清申请人、用途、授权范围、有效期和复审人。“紧急”不能等于跳过确认。我们可以缩短审批流程，但不能省掉记录，也不能把 AI 说可行当作三方批准。
```

### M05｜协调员：聚焦共同问题

```text
目前共同点是：愿意用合成数据合作，不要求原始患者数据跨境。分歧是：正常更新多快、谁能批准提频、谁能暂停。我先请 AI 帮我们梳理依据，再请各方判断，AI 不替任何一方作决定。
```

### 同步镜头（可选，15 秒）

第二窗口打开同一案例的会议室，发送 M03 后切过去展示出现的同一条消息。通常随约两秒一次的同步刷新出现，网络延迟可能更久。不要发送两次来“催出消息”。一个账户开两个窗口展示的是共享同步，不证明已经有独立账户权限系统。

### AI 请求一：把讨论整理成可审核的差异

1. 向下找到“让 AI 帮你问清楚、找依据”。
2. 可先点“分析差异地图”，再用下列完整文字替换“向 AI 提问”。快捷按钮只填问题，不会自动调用。
3. 阅读并勾选发送至 ACCTOKEN／DeepSeek 的同意说明，然后点击“发送给 AI”。不要录制或粘贴密钥。

```text
我们正在进行 DEMO-01 虚构教学演示，请优先依据带 DEMO-01 标记的本轮会议及其后的讨论、三方当前共享立场，区分本轮内容与历史记录；若不确定来源属于哪一轮，请明确说明。请用简短中文列出：1.共同目标；2.更新频率、本地决定权、审批留痕之间的三处张力；3.每处张力对应的原文引用；4.可供人工核对的地图关联；5.下一步需要向三方确认的问题。不得把讨论中的赞同当成正式表态，不得宣布已达成共识。本轮仅使用合成数据，不提供真实医疗或法律结论。
```

4. 等到真实结果出现。展开“核对引用原文”，展示至少一处引文对应刚才的立场或消息。
5. 如果出现合理的“待人工审核的地图关联”，展开“查看依据后决定”，核对后才点击“我已核对，加入地图”。如果没有合适建议，直接按下一节手工建立，不要强行采纳。

### AI 的预期检查点，不是预设答案

- 能否分清研究方的时效目标与“必须获取原始数据”不是一回事？
- 能否识别医院方既关心工作负担，也关心决定权？
- 能否把“快速审核”与“免审核”区分开？
- 引用是否真实对应页面原文？是否误把旧消息当成本轮结论？

真实输出措辞与建议数量不可保证。本脚本没有替 AI 编写一段假装实时生成的回答。若结果有误，可直接讲：“这条建议误读了参与方，所以我们不采纳。”这本身也是有效的演示。

### 旁白

> AI 的价值是让问题更清楚、让依据更容易检查。它既不是裁判，也不是第四个有表决权的参与方。这里的分析来自一次真实请求，只有人核对后，建议才会进入地图。

## 14. 不要在演示中夸大的能力

- 当前是演示角色切换，不是账号绑定或真实机构签署。
- AI 经已配置的第三方平台调用；每次主动发送可能产生费用，刷新历史不会调用模型。脚本建议一到两次真实请求，不承诺固定返回内容和费用。
- AI 面板当前读取本案例共享立场、议题／方案、最近消息和部分历史问答；不会自动看到尚未提交的草稿，也没有自动读取完整和议书或承诺任务的专属流程。
- AI 不自动提案、不替三方接受、不判定现实医疗或法律合规。
- 地图是有来源的关系图，不是自动给参与方打分或判断谁正确。
- 消息通过周期性同步更新，不承诺毫秒级即时通信。
- 任务材料为文本、编号或链接；没有附件上传，也不会自动核验材料真实性。
- 日期提示在打开页面时更新；没有后台邮件或推送提醒。
- 系统不会按文书约定自动运行科研、传输数据、开关授权或执行暂停。
- 导出的确认记录不是电子签名证书；“三方已确认”表达当前演示流程状态。

## 15. 拍完以后逐项核对

- [ ] 画面明确说明虚构教学情境，保留历史，不暗示全新空白项目。
- [ ] 三方各自的目标、担忧、底线与可协商条件至少展示一次。
- [ ] 会议室角色正确，消息实际发送成功。
- [ ] AI 若被介绍为真实调用，镜头中有本次实际返回和可核对引用；失败未伪装成成功。
- [ ] 地图展示了至少一个张力、一个原文依据和当前方案的需求回应。
- [ ] 第一稿五项完整，但医院仍反对，系统未误判为共识。
- [ ] 修订稿把反对条件写进正文，三方再次分别接受。
- [ ] 三项配套方案均确认；没有把任一配套缺失的规则说成完整试点。
- [ ] 和议书有共同目的、边界、责任条款、适用期、保留分歧、复审、暂停和退出。
- [ ] 三方确认整份同一文书版本，而不是只确认方案。
- [ ] 实际打开导出文件，状态与页面选中的版本一致。
- [ ] 如拍履约，明确标注虚构材料；“待验收”与“已验收”两个状态都出现。
- [ ] 收尾表达“形成共同规则”，不是“消除所有差异”。

这支 Demo 最值得记住的三个画面：**填满五项仍可被反对 → 条件真正进入修订正文 → 同一整份文书由三方分别确认。**
